## 二叉搜索树的优势



普通的二叉树，节点是乱放的。但如果我们给节点的摆放定一个死规矩：

> **任何一个节点，它的左子树里所有数字都比它小，右子树里所有数字都比它大。**

这种严格规定了顺序的树，叫做**二叉搜索树（BST）**。

这种树有一个极其神奇的魔力：**只要你对它进行中序遍历，打印出来的序列永远是绝对从小到大排好序的。**

### 性能的提升在哪里？

假设我们要在一堆数字里**查找 7**。

- **没有这棵树时（普通数组）**：数字是乱序的 `[3, 1, 9, 7, 5]`。你要找 7，只能从第一个开始挨个往后看，直到找到为止。如果有一万个数字，你可能要找一万次。
- **有了这棵树时（二叉搜索树）**：你想找 7，你根本不需要去遍历整棵树！你只要站在根节点。

> - 根节点是 5。因为 7 > 5，根据规矩，7 **绝对不可能**在左边。你瞬间就砍掉了左边所有的数字（不需要去遍历它们了），直接往右边走。
> - 到了右边，节点是 8。因为 7 < 8，你瞬间又砍掉了 8 右边的所有数字，直接往左边走。

**这就是性能的提升**：你每走一步，就帮中序遍历砍掉了将近一半的无用功。原本要找一万次，现在可能只需要找十几次。

假设我们有 3 个节点，其全序关系为 `1 < 2 < 3`。无论树怎么变，中序遍历永远是 `[1, 2, 3]`。

- **形态 A（高瘦 - 倾斜链表）**：根节点为 1，1 的右子树是 2，2 的右子树是 3。
  - 查找 1：比较 1 次。
  - 查找 2：比较 2 次。
  - 查找 3：比较 3 次。
  - **最坏时间复杂度**：$O(N)$。
- **形态 B（矮胖 - 严格平衡）**：根节点为 2，2 的左子树是 1，2 的右子树是 3。
  - 查找 2：比较 1 次。
  - 查找 1：比较 2 次。
  - 查找 3：比较 2 次。
  - **最坏时间复杂度**：$O(\log N)$。

## 好景不长（什么是失衡，插入顺序对二叉搜索树性能的破坏）

**由于插入顺序的原因，导致树长歪了、往一边倾斜、变成了一条线**的现象，就叫做**失衡**。失衡会导致我们辛辛苦苦建立的二叉搜索树，失去快速查找的超能力。

## 旋转对失衡的补救

树长歪了，我们就得把它扶正。计算机科学家想出的办法，叫做**旋转（Rotation）**。

旋转的唯一目的：**在绝对不破坏“中序遍历有序性”的前提下，把树的结构变矮、变胖。**

两个节点是不能判定失衡的，因为两点之间就是一条直线

三个节点才可以，而且这是局部解耦的，可以判断失衡。

失衡的类型一共有四种，LL，LR，RL，RR。

祖父，父亲，孩子节点。对于曲线，先对父亲进行一次旋转变成直线，然后再对祖父进行一次旋转即可。对于曲线直接对祖父节点进行旋转就好了。



## 旋转的缺点

**频繁的旋转是非常消耗时间的。** 如果你有一百万个节点，插入一个新数字可能导致整棵树从底层到顶层引发连环塌方一样的旋转，这就好比为了换个轮胎，把整辆车都拆了重装。

所以我们以结构上的瑕疵来极大程度地减少旋转的频率。红黑树的逻辑是：

1. 我们不要追求完美的、一丁点都不歪的平衡（那样旋转太累了）。
2. 我们允许树有轻微的倾斜（比如左边比右边稍微长一点点）。
3. **颜色，就是用来测量“倾斜程度”的标尺。**

红黑树给节点涂上红黑两色，并规定“红色不能连续”等规则。这就好比在树的各个分支上装了“红绿灯传感器”。

- 如果插入新节点后，红绿灯没有报警，说明树虽然歪了一点，但在容忍范围内，**不需要旋转**，直接收工。
- 只有当红绿灯报警了（比如违反了颜色规则），说明树歪得太厉害了，这时候才去触发**旋转**。



## 来点语法说明

```c++
// 这是一个针对 int 的特化红黑树
template <>
class RBTree<int>
{
public:
    // 注意！他在这里没有定义 struct RBTreeNode
    // 而是定义了一个静态成员变量（一个整数），也叫 RBTreeNode！
    static int RBTreeNode; 
};

// 初始化这个静态变量
int RBTree<int>::RBTreeNode = 100;
```



面对没有typename声明的时候，编译器看到了这个

```c++
RBTree<T>::RBTreeNode * node;
```

此时RBTree<T>::RBTreeNode可能是变量数据也有可能是类型，所以编译器混乱了，它根本不知道这是乘法还是指针声明。
